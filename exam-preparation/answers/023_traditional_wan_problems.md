# Назовите основные проблемы традиционных корпоративных глобальных сетей

## Краткий ответ
Традиционные корпоративные глобальные сети (WAN) сталкиваются с рядом критических проблем: высокая стоимость каналов связи и оборудования, сложность управления и конфигурации, недостаточная гибкость и масштабируемость, проблемы с производительностью при работе с облачными приложениями, длительные сроки развертывания новых подключений, ограниченная видимость трафика, зависимость от MPLS провайдеров, сложность обеспечения безопасности и отказоустойчивости. Эти проблемы привели к появлению современных решений SD-WAN.

## Развёрнутый ответ

### 1. Высокая стоимость

#### Капитальные затраты (CapEx)

**Дорогостоящее оборудование:**
- Корпоративные маршрутизаторы (Cisco ISR, Juniper SRX): $5,000 - $50,000+ за устройство
- MPLS CPE (Customer Premises Equipment)
- Специализированное WAN оптимизационное оборудование
- Резервное оборудование для обеспечения отказоустойчивости
- Стоимость замены устаревшего оборудования каждые 3-5 лет

**Инфраструктура филиалов:**
```
Типичная стоимость оборудования для филиала:
- Маршрутизатор: $8,000
- Firewall: $5,000
- WAN optimizer: $10,000
- Резервные устройства: +50%
Итого: ~$35,000 на филиал

При 100 филиалах: $3,500,000
```

#### Операционные затраты (OpEx)

**MPLS каналы:**
- Значительно дороже интернет-каналов (в 3-10 раз)
- Стоимость зависит от bandwidth и SLA
- Дополнительные расходы за overage (превышение трафика)
- Длительные контракты (обычно 3 года)

**Сравнение стоимости каналов:**
```
Пример ежемесячной стоимости (10 Mbps):
- MPLS канал: $1,500 - $3,000
- Обычный интернет: $300 - $500
- Fiber DIA: $800 - $1,200

Для 50 филиалов с MPLS:
$1,500 × 50 = $75,000/месяц = $900,000/год
```

**Техническая поддержка:**
- Специализированный персонал для управления WAN
- Высокая квалификация требуется
- 24/7 мониторинг и поддержка
- Обучение персонала работе с оборудованием

### 2. Сложность управления

#### Децентрализованная конфигурация

**Индивидуальная настройка устройств:**
- Каждый маршрутизатор настраивается отдельно
- Различные версии ПО и конфигураций
- Отсутствие централизованной консоли управления
- Сложность поддержания консистентности политик

**Пример:**
```
Изменение ACL для доступа к новому приложению:
1. Подключиться к каждому из 100 маршрутизаторов
2. Внести изменения в конфигурацию
3. Протестировать изменения
4. Документировать изменения

Время: 10-20 минут × 100 устройств = 16-33 часа работы
Риск ошибок: высокий
```

#### Множество интерфейсов управления

**Разнородные системы:**
- CLI для маршрутизаторов
- Web-interface для firewall
- Отдельная консоль для WAN optimization
- Различные системы мониторинга
- Отсутствие единой точки управления

**Проблемы:**
- Необходимость знания различных синтаксисов команд
- Сложность автоматизации
- Увеличение времени на администрирование
- Высокая вероятность человеческих ошибок

#### Управление политиками безопасности

**Распределенные firewall правила:**
```
Проблема: Применение новой политики безопасности
- 50 филиалов с firewall
- Необходимо добавить правило для нового приложения
- Каждый firewall настраивается индивидуально
- Различные версии firmware и feature sets
- Сложность audit и compliance проверки
```

### 3. Недостаточная гибкость и масштабируемость

#### Статическая конфигурация

**Жесткие топологии:**
- Hub-and-spoke архитектура (все через центральный ЦОД)
- Сложность изменения топологии
- Невозможность динамической маршрутизации трафика
- Фиксированные bandwidth allocation

**Проблема hub-and-spoke:**
```
Сценарий: Филиал A хочет связаться с Филиалом B

Неоптимальный путь:
Филиал A → Головной офис (ЦОД) → Филиал B
- Удвоение latency
- Использование bandwidth головного офиса
- Bottleneck в ЦОД

Оптимальный путь (недоступен):
Филиал A → прямое соединение → Филиал B
```

#### Долгое развертывание

**Время подключения новых локаций:**
```
Типичный процесс подключения филиала через MPLS:
1. Заказ канала у провайдера: 30-90 дней
2. Физическая установка: 1-2 недели
3. Настройка оборудования: 1-3 дня
4. Тестирование: 1-2 дня
Итого: 2-4 месяца

Проблемы:
- Невозможность быстро открыть новый офис
- Зависимость от провайдера
- Сложность временных подключений
```

#### Ограниченная масштабируемость

**Проблемы роста:**
- Увеличение числа филиалов усложняет управление линейно
- Конфигурация становится всё более complex
- MPLS mesh топологии дороги (n×(n-1)/2 соединений)
- Ограничения по числу BGP/OSPF соседств

### 4. Проблемы с производительностью облачных приложений

#### Backhauling трафика

**Неоптимальная маршрутизация:**
```
Проблема: Доступ к Office 365/SaaS из филиала

Традиционная архитектура:
Пользователь (Филиал) →
MPLS →
Головной офис (firewall/proxy) →
Internet →
Office 365

Проблемы:
- Увеличенная latency (200+ ms вместо 20-50 ms)
- Bottleneck в ЦОД
- Неэффективное использование дорогого MPLS
- Плохой user experience
```

**Влияние на production:**
```
Сравнение latency:
Прямой доступ к облаку: 20-30 ms
Через backhauling: 150-300 ms

Влияние:
- Video conferencing: плохое качество
- VoIP: задержки и jitter
- Cloud applications: медленная работа
- File sync (Dropbox/OneDrive): timeouts
```

#### Ограниченная bandwidth

**Недостаточная пропускная способность:**
- MPLS каналы часто 10-50 Mbps (дорого увеличивать)
- Современные приложения требуют больше
- Video collaboration (Zoom/Teams) потребляет значительную bandwidth
- Cloud backup перегружает каналы

**Примеры потребления bandwidth:**
```
Современные приложения:
- HD video conference: 2-4 Mbps per user
- 4K video conference: 8-12 Mbps per user
- Cloud backup: может занять весь канал
- Software updates: гигабайты данных

Филиал с 50 сотрудниками:
- 10 одновременных video calls: 40 Mbps
- Background syncing: 20 Mbps
- Regular traffic: 30 Mbps
Требуется: 90+ Mbps

Имеется MPLS: 20 Mbps → перегрузка
```

### 5. Отсутствие видимости и контроля

#### Ограниченная аналитика

**Проблемы мониторинга:**
- Традиционные инструменты показывают только утилизацию каналов
- Нет visibility на уровне приложений
- Сложность определения причин проблем
- Отсутствие реального real-time мониторинга

**Что не видно:**
```
Традиционный мониторинг:
✓ Bandwidth utilization
✓ Packet loss
✓ Latency (basic)
✗ Application performance
✗ User experience metrics
✗ Cloud application quality
✗ Детальная аналитика трафика
```

#### Реактивное управление

**Обнаружение проблем:**
- Проблемы выявляются через user complaints
- Нет proactive alerting
- Долгое время troubleshooting
- Отсутствие исторических данных для анализа

**Типичный сценарий:**
```
1. Пользователь жалуется на медленную работу
2. IT начинает расследование (1-2 часа)
3. Проверка различных компонентов
4. Обращение к провайдеру (если проблема в канале)
5. Ожидание ответа провайдера (часы/дни)
6. Решение проблемы

Время простоя: часы или дни
Business impact: значительный
```

### 6. Безопасность и compliance

#### Распределенная безопасность

**Проблемы:**
- Firewall на каждом филиале требует индивидуальной настройки
- Сложность поддержания единых политик безопасности
- Различные версии firmware и signature databases
- Риск misconfiguration

**Compliance вызовы:**
```
Требования: PCI DSS, HIPAA, GDPR

Сложности:
- Audit всех устройств на compliance
- Доказательство применения политик везде
- Tracking изменений конфигурации
- Централизованное logging для всех филиалов
```

#### Недостаточная защита от угроз

**Ограничения:**
- Branch firewall имеют ограниченные возможности
- Нет advanced threat protection на периметре филиала
- SSL/TLS inspection перегружает устройства
- Устаревшие signature databases

### 7. Vendor lock-in и зависимость от провайдера

#### MPLS зависимость

**Проблемы:**
- Привязка к одному или нескольким MPLS провайдерам
- Долгосрочные контракты (3+ года)
- Сложность смены провайдера
- Ограниченная географическая доступность

**Последствия:**
```
Смена MPLS провайдера:
1. Разрыв существующих контрактов (штрафы)
2. Заказ новых каналов (2-4 месяца)
3. Параллельная работа двух сетей
4. Миграция филиалов по одному
5. Обучение персонала новым процедурам

Время: 6-12 месяцев
Стоимость: значительная
Риск: высокий
```

#### Vendor lock-in оборудования

**Проблемы:**
- Привязка к конкретному вендору (Cisco, Juniper)
- Проприетарные протоколы и feature sets
- Дорогостоящие лицензии
- Необходимость специализированных навыков

### 8. Отсутствие отказоустойчивости

#### Single point of failure

**Проблемы:**
```
Типичная архитектура филиала:
- Один MPLS канал
- Один маршрутизатор
- Один firewall

При отказе любого компонента:
→ Полная потеря connectivity
→ Downtime до устранения проблемы (часы/дни)
```

**Стоимость простоя:**
- Loss of productivity
- Недоступность критичных приложений
- Влияние на бизнес-процессы
- Репутационные риски

#### Дорогая избыточность

**Двойной MPLS:**
```
Стоимость отказоустойчивости:
Primary MPLS: $2,000/месяц
Backup MPLS: $2,000/месяц
Итого: $4,000/месяц на филиал

Для 50 филиалов: $200,000/месяц = $2.4M/год

Проблема: очень дорого для SMB
Результат: большинство филиалов без redundancy
```

### 9. Сложность поддержки новых технологий

#### Интеграция с облаком

**Проблемы:**
- Традиционная WAN не оптимизирована для cloud
- Необходимость backhauling cloud трафика
- Сложность direct internet breakout
- Отсутствие cloud-native функций

#### IoT и Edge Computing

**Ограничения:**
- Недостаточная bandwidth для IoT устройств
- Отсутствие edge processing capabilities
- Сложность масштабирования для множества устройств
- Проблемы с real-time обработкой данных

### 10. Операционная сложность

#### Troubleshooting

**Проблемы диагностики:**
```
Типичный процесс troubleshooting:
1. Пользователь сообщает о проблеме
2. Helpdesk пытается воспроизвести
3. Escalation к network team
4. Анализ логов множества устройств
5. Возможно обращение к провайдеру
6. Ожидание ответа провайдера

Время решения: часы или дни
Tools: разрозненные, неэффективные
```

#### Change management

**Сложность изменений:**
- Каждое изменение требует тщательного планирования
- Риск break что-то в production
- Необходимость maintenance windows
- Rollback процедуры сложны

**Пример:**
```
Обновление ACL на всех маршрутизаторах:
- Planning: 2 часа
- Testing на lab: 4 часа
- Implementation: 8+ часов (по филиалам)
- Validation: 4 часа
Итого: 2-3 дня работы

При ошибке: откат на всех устройствах
```

### Эволюция: SD-WAN как решение

Современные SD-WAN решения адресуют большинство перечисленных проблем:

**Ключевые улучшения:**
- **Стоимость**: использование интернет-каналов вместо MPLS
- **Управление**: централизованная оркестрация
- **Гибкость**: программно-определяемые политики
- **Производительность**: direct cloud access, application-aware routing
- **Видимость**: real-time аналитика
- **Безопасность**: integrated security, centralized policies
- **Независимость**: vendor-agnostic, multi-transport
- **Отказоустойчивость**: active-active multi-path
- **Облако**: cloud-first архитектура
- **Операции**: автоматизация, zero-touch provisioning

# Что такое вертикальное масштабирование?

## Краткий ответ
Вертикальное масштабирование (vertical scaling или scale up/down) — это увеличение или уменьшение вычислительных ресурсов отдельного узла или контейнера путем добавления/удаления CPU, памяти, дискового пространства. В контексте контейнеров это изменение лимитов и запросов ресурсов для работающего pod/контейнера без изменения количества экземпляров.

## Развёрнутый ответ

### Определение вертикального масштабирования

Вертикальное масштабирование (Vertical Scaling, Scale Up/Down) — это метод увеличения производительности системы путем добавления ресурсов к существующему узлу или экземпляру приложения. Это противоположность горизонтальному масштабированию, при котором добавляются новые экземпляры.

### Как работает вертикальное масштабирование

**В традиционной инфраструктуре:**
- Увеличение количества CPU в сервере
- Добавление оперативной памяти (RAM)
- Расширение дискового пространства
- Переход на более мощное оборудование

**В контейнерной среде:**
- Изменение resource limits и requests для контейнеров
- Увеличение размера инстанса VM, на котором работает узел кластера
- Динамическое изменение выделенных ресурсов без перезапуска (в некоторых оркестраторах)

### Вертикальное масштабирование в Kubernetes

**Resource Requests и Limits:**
```yaml
resources:
  requests:
    memory: "64Mi"
    cpu: "250m"
  limits:
    memory: "128Mi"
    cpu: "500m"
```

**Vertical Pod Autoscaler (VPA):**
- Автоматический компонент Kubernetes, который анализирует использование ресурсов
- Рекомендует или автоматически изменяет requests/limits
- Работает в трех режимах: Off (только рекомендации), Initial (при создании), Auto (автоматическое обновление)

**Процесс вертикального масштабирования pod:**
1. VPA анализирует метрики использования ресурсов
2. Определяет оптимальные значения requests/limits
3. Удаляет существующий pod
4. Создает новый pod с обновленными ресурсами
5. Scheduler размещает pod на подходящем узле

### Вертикальное масштабирование в Docker Swarm

**Обновление resource constraints:**
```bash
docker service update --limit-cpu 2 --limit-memory 2G my-service
docker service update --reserve-cpu 1 --reserve-memory 1G my-service
```

**Изменение для отдельного контейнера:**
```bash
docker update --cpus="2.0" --memory="2g" container_name
```

### Преимущества вертикального масштабирования

**Простота реализации:**
- Не требует изменения архитектуры приложения
- Приложение не нужно адаптировать для работы в распределенной среде
- Один экземпляр проще мониторить и отлаживать

**Отсутствие накладных расходов на координацию:**
- Не нужна синхронизация между экземплярами
- Отсутствие проблем с распределенным состоянием
- Нет необходимости в балансировке нагрузки

**Подходит для stateful приложений:**
- Базы данных часто требуют вертикального масштабирования
- Не нужно решать проблемы с консистентностью данных
- Упрощенное управление транзакциями

**Эффективность для определенных задач:**
- Однопоточные приложения получают больше выигрыша от мощного CPU
- Приложения с большими объемами данных в памяти
- Задачи, требующие высокой скорости межпроцессного взаимодействия

### Недостатки вертикального масштабирования

**Физические ограничения:**
- Существует предел размера одного сервера
- Максимальное количество CPU, памяти, дисков
- Дальнейшее масштабирование невозможно

**Простой при масштабировании:**
- В большинстве случаев требуется перезапуск приложения
- В Kubernetes VPA требует пересоздания pod
- На традиционных серверах — полный shutdown для замены железа

**Высокая стоимость:**
- Мощное оборудование стоит непропорционально дороже
- Удвоение ресурсов может стоить в 3-4 раза дороже
- Cloud instances большего размера имеют более высокую цену за единицу ресурса

**Единая точка отказа (SPOF):**
- Если узел выходит из строя, приложение полностью недоступно
- Нет автоматической отказоустойчивости
- Требуются дополнительные меры для обеспечения HA

**Неэффективное использование ресурсов:**
- Если нагрузка падает, ресурсы простаивают
- Невозможно быстро уменьшить capacity без простоя
- "Переплата" за ресурсы в периоды низкой нагрузки

**Ограничения в облачных средах:**
- Многие managed Kubernetes сервисы ограничивают размер node
- Изменение размера инстанса требует его пересоздания
- Не все типы инстансов доступны во всех регионах

### Сценарии использования вертикального масштабирования

**Идеально подходит для:**
- Монолитных приложений, не поддерживающих горизонтальное масштабирование
- Базы данных (PostgreSQL, MySQL) при умеренной нагрузке
- In-memory кэши и очереди сообщений
- Приложения с лицензированием по количеству экземпляров
- Legacy системы, которые невозможно переписать

**Не подходит для:**
- Микросервисных архитектур
- Stateless веб-приложений с переменной нагрузкой
- Приложений, требующих высокой доступности
- Систем с непредсказуемыми пиками нагрузки

### Комбинирование вертикального и горизонтального масштабирования

В современных системах часто используется **гибридный подход**:

**Вертикальное для отдельных компонентов:**
- База данных масштабируется вертикально до определенного предела
- Затем применяется шардирование (горизонтальное масштабирование)

**Горизонтальное для stateless компонентов:**
- Frontend и API серверы масштабируются горизонтально
- Каждый экземпляр настроен вертикально под оптимальную нагрузку

**Многоуровневое масштабирование:**
- Сначала увеличиваются ресурсы существующих pod (вертикально)
- При достижении лимитов добавляются новые реплики (горизонтально)
- Узлы кластера также могут масштабироваться обоими способами

### Инструменты автоматизации вертикального масштабирования

**Kubernetes Vertical Pod Autoscaler (VPA):**
- Мониторит использование ресурсов pod
- Предоставляет рекомендации или автоматически обновляет resources
- Интегрируется с metrics-server

**Cloud-specific autoscalers:**
- AWS Auto Scaling для изменения типа EC2 instance
- GCP Instance Right-sizing recommendations
- Azure VM size recommendations

**Сторонние решения:**
- Goldilocks — визуализация рекомендаций VPA
- Kruise — расширенное управление workloads с in-place updates

### Практические рекомендации

**Мониторинг перед масштабированием:**
- Анализируйте метрики использования CPU, памяти, I/O
- Выявляйте бутылочные горлышки — не всегда проблема в ресурсах
- Используйте профилирование приложений

**Постепенное увеличение:**
- Не увеличивайте ресурсы резко в несколько раз
- Проверяйте влияние каждого изменения на производительность
- Учитывайте, что приложение может не использовать дополнительные ресурсы эффективно

**Планирование downtime:**
- Если перезапуск неизбежен, выбирайте время минимальной нагрузки
- Уведомляйте пользователей заранее
- Подготовьте план отката к предыдущей конфигурации

**Оптимизация кода перед масштабированием:**
- Часто проблемы производительности решаются оптимизацией кода
- Вертикальное масштабирование может маскировать неэффективный код
- Профилируйте приложение для поиска узких мест

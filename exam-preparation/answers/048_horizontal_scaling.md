# Что такое горизонтальное масштабирование?

## Краткий ответ
Горизонтальное масштабирование (horizontal scaling или scale out/in) — это увеличение или уменьшение производительности системы путем добавления или удаления экземпляров приложения. В контейнерной среде это означает изменение количества реплик (pods, контейнеров) сервиса, которые работают параллельно и обрабатывают запросы за балансировщиком нагрузки.

## Развёрнутый ответ

### Определение горизонтального масштабирования

Горизонтальное масштабирование (Horizontal Scaling, Scale Out/In) — это метод увеличения пропускной способности системы путем добавления большего количества машин или экземпляров приложения, работающих параллельно. При горизонтальном масштабировании вместо увеличения мощности одного сервера добавляются новые серверы с аналогичной конфигурацией.

### Принцип работы

**Scale Out (масштабирование наружу):**
- Добавление новых экземпляров приложения
- Увеличение количества реплик в оркестраторе
- Распределение нагрузки между большим количеством узлов

**Scale In (масштабирование внутрь):**
- Удаление избыточных экземпляров при снижении нагрузки
- Уменьшение количества реплик
- Оптимизация использования ресурсов и снижение затрат

### Горизонтальное масштабирование в Kubernetes

**Ручное масштабирование:**
```bash
kubectl scale deployment my-app --replicas=5
```

**Декларативное описание:**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 5
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: app
        image: my-app:v1
```

**Horizontal Pod Autoscaler (HPA):**
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: my-app-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: my-app
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 80
```

**Метрики для автомасштабирования:**
- CPU utilization (использование процессора)
- Memory utilization (использование памяти)
- Custom metrics (длина очереди, количество запросов в секунду, время ответа)
- External metrics (метрики из внешних систем, например, Prometheus)

### Горизонтальное масштабирование в Docker Swarm

**Масштабирование сервиса:**
```bash
docker service scale my-service=5
```

**Обновление количества реплик:**
```bash
docker service update --replicas 5 my-service
```

**В docker-compose.yml:**
```yaml
version: '3.8'
services:
  web:
    image: my-app:latest
    deploy:
      replicas: 5
      update_config:
        parallelism: 2
        delay: 10s
```

### Компоненты горизонтального масштабирования

**Балансировщик нагрузки (Load Balancer):**
- Распределяет входящие запросы между всеми доступными репликами
- Выполняет health checks для исключения неработающих экземпляров
- Алгоритмы: Round Robin, Least Connections, IP Hash

**Service Discovery:**
- Автоматическое обнаружение новых экземпляров
- Обновление конфигурации балансировщика при изменении количества реплик
- DNS-based или API-based discovery

**Shared Storage/Database:**
- Общее хранилище данных для всех экземпляров
- База данных, доступная всем репликам
- Distributed cache (Redis, Memcached)

**Session Management:**
- Sticky sessions (привязка пользователя к конкретному экземпляру)
- Shared session storage (Redis, database)
- Stateless design с JWT токенами

### Преимущества горизонтального масштабирования

**Практически неограниченная масштабируемость:**
- Можно добавлять серверы до физических пределов дата-центра
- Легко достигать десятков тысяч экземпляров (например, Netflix, Google)
- Масштабирование определяется потребностями, а не ограничениями железа

**Высокая отказоустойчивость:**
- Отказ одного экземпляра не влияет на доступность сервиса
- Автоматическое перераспределение нагрузки на оставшиеся реплики
- Возможность rolling updates без downtime

**Эффективность затрат:**
- Можно использовать commodity hardware (стандартное недорогое оборудование)
- Добавление ресурсов пропорционально стоимости
- В облаке — оплата только за используемые ресурсы

**Гибкость масштабирования:**
- Быстрое добавление capacity при пиковых нагрузках
- Автоматическое уменьшение при снижении трафика
- Адаптация к динамике бизнеса без избыточных инвестиций

**Географическое распределение:**
- Размещение реплик в разных регионах
- Снижение задержек для пользователей
- Соответствие требованиям локального хранения данных (data residency)

**Постепенное масштабирование:**
- Добавление ресурсов без простоя
- Инкрементальное увеличение capacity
- Тестирование нагрузки на дополнительных экземплярах

### Недостатки горизонтального масштабирования

**Сложность архитектуры:**
- Приложение должно быть спроектировано для работы в распределенной среде
- Необходимость управления состоянием (stateless design)
- Сложность отладки и трассировки запросов через множество экземпляров

**Проблемы с консистентностью данных:**
- Распределенные транзакции сложны в реализации
- CAP теорема — компромисс между консистентностью, доступностью и устойчивостью к разделению
- Eventual consistency вместо strong consistency

**Overhead на координацию:**
- Балансировка нагрузки добавляет задержки
- Межсервисное взаимодействие по сети медленнее, чем локальные вызовы
- Необходимость в service mesh для управления коммуникацией

**Сложность управления сессиями:**
- Sticky sessions снижают эффективность балансировки
- Shared session storage — дополнительная зависимость и точка отказа
- Stateless design требует переработки legacy приложений

**Лицензирование:**
- Некоторое ПО лицензируется по количеству экземпляров
- Стоимость лицензий может расти непропорционально
- Коммерческие базы данных часто требуют per-instance лицензии

**Увеличение операционной сложности:**
- Мониторинг множества экземпляров
- Управление конфигурацией и обновлениями
- Отладка проблем, возникающих только при определенной нагрузке

### Требования к приложению для горизонтального масштабирования

**Stateless дизайн:**
- Приложение не хранит состояние локально
- Вся необходимая информация в запросе или внешнем хранилище
- Любой экземпляр может обработать любой запрос

**Shared-nothing или shared-storage архитектура:**
- Нет зависимости от локальных файлов на диске
- Используется общая база данных или object storage (S3, GCS)
- Distributed file systems (NFS, GlusterFS, Ceph)

**Идемпотентность операций:**
- Повторное выполнение операции дает тот же результат
- Защита от дублирования запросов при retries
- Использование transaction IDs или idempotency keys

**Горизонтально масштабируемые зависимости:**
- База данных должна поддерживать масштабирование (sharding, read replicas)
- Cache layer (Redis Cluster, Memcached)
- Message queues (Kafka, RabbitMQ)

### Паттерны горизонтального масштабирования

**Active-Active (все экземпляры активны):**
- Все реплики обрабатывают запросы одновременно
- Балансировщик распределяет нагрузку равномерно
- Максимальная утилизация ресурсов

**Active-Passive (активный-резервный):**
- Один экземпляр обрабатывает запросы, остальные в standby
- При отказе активного переключение на резервный
- Используется для stateful приложений

**Sharding (разделение данных):**
- Данные разделяются между экземплярами по ключу (user ID, geography)
- Каждый shard обрабатывает свою часть данных
- Применяется для баз данных и кэшей

**Read replicas:**
- Master для записи, множество replicas для чтения
- Масштабирование read-heavy workloads
- Eventual consistency между репликами

### Автомасштабирование (Auto-scaling)

**На основе метрик ресурсов:**
- CPU utilization выше 70% → добавить реплики
- Memory utilization выше 80% → добавить реплики
- Усреднение метрик за период (обычно 1-5 минут)

**На основе пользовательских метрик:**
- Requests per second (RPS)
- Average response time
- Queue depth (длина очереди задач)
- Active connections

**Предиктивное масштабирование:**
- Анализ исторических паттернов нагрузки
- Масштабирование до наступления пика
- Machine Learning для прогнозирования

**Scheduled scaling:**
- Масштабирование по расписанию
- Увеличение capacity перед известными событиями
- Уменьшение в ночное время или выходные

### Стратегии развертывания при масштабировании

**Rolling Update:**
- Постепенная замена старых реплик новыми
- Всегда доступно минимальное количество экземпляров
- Возможность отката при проблемах

**Blue-Green Deployment:**
- Развертывание новой версии параллельно со старой
- Переключение трафика на новую версию одномоментно
- Быстрый откат при необходимости

**Canary Deployment:**
- Новая версия разворачивается на небольшом проценте реплик
- Постепенное увеличение трафика на новую версию
- Мониторинг метрик перед полным развертыванием

### Практические сценарии использования

**Веб-приложения и API:**
- Stateless серверы за load balancer
- Автоматическое масштабирование при изменении трафика
- Идеальный кейс для горизонтального масштабирования

**Микросервисы:**
- Каждый сервис масштабируется независимо
- Масштабирование только узких мест системы
- Эффективное использование ресурсов

**Worker pools (обработка фоновых задач):**
- Масштабирование на основе длины очереди
- Параллельная обработка большого объема задач
- Автоматическое уменьшение при отсутствии задач

**Streaming и data processing:**
- Обработка потоков данных в реальном времени
- Масштабирование на основе throughput
- Kafka consumers, Spark executors

### Мониторинг и отладка

**Ключевые метрики:**
- Количество активных реплик
- Распределение нагрузки между репликами
- Response time percentiles (p50, p95, p99)
- Error rate по репликам

**Инструменты:**
- Prometheus + Grafana для метрик
- Jaeger, Zipkin для distributed tracing
- ELK/EFK stack для логирования
- Service mesh (Istio, Linkerd) для observability

**Проблемы и их диагностика:**
- Unbalanced load — проверить алгоритм балансировки
- Slow scaling — настроить агрессивность HPA
- Flapping (частое масштабирование вверх-вниз) — увеличить stabilization window

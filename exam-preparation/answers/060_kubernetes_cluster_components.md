# Из чего состоит кластер Kubernetes?

## Краткий ответ
Кластер Kubernetes состоит из **Control Plane (плоскости управления)** и **Worker Nodes (рабочих узлов)**. Control Plane включает: kube-apiserver (API сервер), etcd (хранилище), kube-scheduler (планировщик), kube-controller-manager (менеджер контроллеров) и cloud-controller-manager (для облачных интеграций). Worker Nodes содержат: kubelet (агент узла), kube-proxy (сетевой прокси) и Container Runtime (среда выполнения контейнеров).

## Развёрнутый ответ

### Архитектура кластера Kubernetes

Кластер Kubernetes представляет собой набор машин (физических или виртуальных), называемых узлами, которые запускают контейнеризированные приложения. Архитектура делится на две основные части: Control Plane и Worker Nodes.

### Control Plane (Плоскость управления)

Control Plane отвечает за управление кластером, принятие глобальных решений (например, планирование) и обнаружение и реагирование на события кластера.

#### Компоненты Control Plane

**1. kube-apiserver**

*Назначение:*
- Предоставляет REST API для взаимодействия с кластером
- Выступает frontend для Control Plane
- Единственный компонент, который напрямую взаимодействует с etcd

*Функции:*
- Аутентификация и авторизация запросов
- Валидация объектов API
- Обработка CRUD операций над ресурсами
- Предоставление watch API для отслеживания изменений

*Масштабируемость:*
- Stateless компонент
- Можно запускать несколько экземпляров для высокой доступности
- Горизонтально масштабируемый

**2. etcd**

*Назначение:*
- Распределённое key-value хранилище
- Единственный источник правды (single source of truth) для состояния кластера
- Хранит всю конфигурацию и состояние кластера

*Данные в etcd:*
- Конфигурация всех объектов Kubernetes
- Состояние всех ресурсов
- Метаданные кластера
- Secrets и ConfigMaps

*Характеристики:*
- Использует алгоритм консенсуса Raft
- Обеспечивает строгую консистентность
- Поддерживает watch для отслеживания изменений
- Требует нечётное количество экземпляров (3, 5, 7)

**3. kube-scheduler**

*Назначение:*
- Отвечает за назначение Pod на узлы
- Отслеживает новые Pod без назначенного узла

*Процесс планирования:*
1. **Фильтрация (Filtering)**: отбор подходящих узлов
   - Проверка требований к ресурсам (CPU, память)
   - Node selectors и affinity/anti-affinity
   - Taints и tolerations
   - PersistentVolume constraints

2. **Оценка (Scoring)**: ранжирование подходящих узлов
   - Балансировка нагрузки
   - Предпочтительное размещение
   - Минимизация межузлового трафика

3. **Назначение (Binding)**: выбор лучшего узла

*Расширяемость:*
- Поддержка кастомных scheduler
- Scheduler extenders
- Multiple schedulers

**4. kube-controller-manager**

*Назначение:*
- Запускает контроллеры кластера
- Каждый контроллер — отдельный процесс, объединённые в один бинарник

*Основные контроллеры:*

- **Node Controller**: отслеживает состояние узлов, реагирует на сбои
- **Replication Controller**: поддерживает правильное количество Pod
- **Endpoints Controller**: создаёт объекты Endpoints для Service
- **Service Account & Token Controllers**: создают default аккаунты и API tokens
- **Deployment Controller**: управляет развёртываниями
- **StatefulSet Controller**: управляет stateful приложениями
- **DaemonSet Controller**: обеспечивает запуск Pod на всех/выбранных узлах
- **Job Controller**: управляет одноразовыми задачами
- **CronJob Controller**: управляет задачами по расписанию
- **ReplicaSet Controller**: поддерживает нужное количество реплик Pod

*Принцип работы:*
- Контроллеры используют control loop (цикл управления)
- Непрерывно сравнивают желаемое состояние с фактическим
- Предпринимают действия для достижения желаемого состояния

**5. cloud-controller-manager**

*Назначение:*
- Интеграция с API облачных провайдеров
- Отделяет логику взаимодействия с облаком от core компонентов

*Контроллеры:*
- **Node Controller**: проверка существования узлов в облаке
- **Route Controller**: настройка маршрутизации в облачной инфраструктуре
- **Service Controller**: создание/удаление облачных балансировщиков нагрузки

*Особенности:*
- Опциональный компонент (не нужен в on-premise)
- Специфичен для каждого облачного провайдера

### Worker Nodes (Рабочие узлы)

Worker Nodes — это машины, на которых выполняются контейнеризированные приложения.

#### Компоненты Worker Nodes

**1. kubelet**

*Назначение:*
- Агент, работающий на каждом узле
- Обеспечивает выполнение контейнеров в Pod

*Функции:*
- Получает PodSpecs от API server
- Обеспечивает запуск и работу контейнеров
- Отслеживает состояние контейнеров
- Отправляет отчёты о состоянии узла и Pod
- Выполняет проверки liveness и readiness probes
- Управляет volumes

*Взаимодействие:*
- Напрямую с Container Runtime через CRI (Container Runtime Interface)
- С API server для получения инструкций и отправки статусов
- Не управляет контейнерами, не созданными через Kubernetes

**2. kube-proxy**

*Назначение:*
- Сетевой прокси, работающий на каждом узле
- Реализует концепцию Service

*Функции:*
- Поддерживает сетевые правила на узлах
- Обеспечивает балансировку нагрузки для Service
- Маршрутизация трафика к Pod

*Режимы работы:*

- **iptables mode** (по умолчанию):
  - Использует правила iptables для маршрутизации
  - Случайный выбор backend Pod
  - Низкие накладные расходы

- **IPVS mode**:
  - Использует Linux IPVS (IP Virtual Server)
  - Больше алгоритмов балансировки (rr, lc, dh, sh, sed, nq)
  - Лучшая производительность для больших кластеров

- **userspace mode** (устаревший):
  - kube-proxy работает как прокси
  - Высокие накладные расходы

**3. Container Runtime**

*Назначение:*
- ПО для запуска контейнеров

*Требования:*
- Реализация Container Runtime Interface (CRI)

*Поддерживаемые runtime:*
- **containerd**: легковесный, промышленный стандарт
- **CRI-O**: легковесный runtime, специально для Kubernetes
- **Docker Engine**: через cri-dockerd (deprecated)
- Другие CRI-совместимые runtime

### Дополнительные компоненты

#### DNS (обычно CoreDNS)
- Кластерный DNS сервер
- Обеспечивает разрешение имён Service и Pod
- Автоматически создаёт DNS записи для Service

#### Network Plugin (CNI)
- Реализует сетевую модель Kubernetes
- Примеры: Calico, Flannel, Weave, Cilium
- Обеспечивает связность между Pod

#### Monitoring и Logging
- **Metrics Server**: сбор метрик ресурсов
- **Prometheus**: мониторинг и алертинг
- **EFK Stack**: Elasticsearch, Fluentd, Kibana для логирования

### Типы узлов

**Master Nodes (Control Plane Nodes)**
- Запускают компоненты Control Plane
- Обычно не запускают пользовательские Pod (taint)
- Требуют высокой доступности (обычно 3 или 5 узлов)

**Worker Nodes**
- Запускают пользовательские приложения
- Масштабируются в зависимости от нагрузки
- Могут быть гетерогенными (разные размеры)

### Коммуникация между компонентами

**Control Plane → Worker Nodes:**
- API server → kubelet (через HTTPS)
- Для управления Pod и получения статусов

**Worker Nodes → Control Plane:**
- kubelet → API server (регистрация, отчёты о состоянии)
- kube-proxy → API server (получение информации о Service)

**Внутри Control Plane:**
- Все компоненты → API server
- Только API server взаимодействует с etcd

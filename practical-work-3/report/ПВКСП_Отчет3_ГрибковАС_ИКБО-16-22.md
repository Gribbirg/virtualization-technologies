Задание 1. Создание Dockerfile с демонстрацией всех команд
:::

::: {custom-style="Normal"}
В рамках первого задания требуется создать один или несколько Dockerfile, в которых каждая из 13 указанных команд Docker используется хотя бы один раз. Был создан Dockerfile для Node.js приложения, демонстрирующий использование всех требуемых директив.
:::

::: {custom-style="Listing"}
Dockerfile с использованием всех 13 команд Docker
:::

::: {custom-style="Code"}
FROM node:18-slim

LABEL maintainer="Student Name <student@example.com>"
LABEL version="1.0"
LABEL description="Dockerfile demonstrating all Docker commands for Task 1"

ENV NODE_ENV=production
ENV PORT=3000
ENV APP_NAME="docker-commands-demo"

WORKDIR /app

RUN groupadd -r appuser && useradd -r -g appuser appuser

COPY package.json ./

RUN apt-get update && \
    apt-get install -y wget && \
    npm install --production && \
    mkdir -p /app/data /app/downloads && \
    apt-get clean && \
    rm -rf /var/lib/apt/lists/*

ADD https://raw.githubusercontent.com/nodejs/node/main/README.md /app/downloads/node-readme.md

COPY . .

RUN chown -R appuser:appuser /app

USER appuser

VOLUME ["/app/data"]

EXPOSE $PORT

ONBUILD COPY . /app
ONBUILD RUN npm install

ENTRYPOINT ["node"]

CMD ["app.js"]
:::

Задание 2. Веб-приложение Spring Boot с PostgreSQL
:::

::: {custom-style="Normal"}
Второе задание требует создания Dockerfile для веб-приложения, написанного с использованием фреймворка Spring Boot и взаимодействующего с СУБД PostgreSQL. Dockerfile должен содержать две изолированные стадии: сборку и запуск jar файла.
:::

::: {custom-style="Normal"}
Приложение реализует три эндпоинта: добавление элемента, вывод списка всех элементов и получение фото герба РТУ МИРЭА. При сборке проекта с помощью утилиты wget загружается файл изображения герба МИРЭА, который затем становится доступным по соответствующему эндпоинту веб-сервиса.
:::

::: {custom-style="Listing"}
Многоэтапный Dockerfile для Spring Boot приложения
:::

::: {custom-style="Code"}
FROM gradle:8.14-jdk21 AS build

LABEL maintainer="Александр Грибков <student@mirea.ru>"
LABEL version="1.0"
LABEL description="Multi-stage Spring Boot application with PostgreSQL"

WORKDIR /app

COPY build.gradle.kts ./
COPY src src

RUN apt-get update && \
    apt-get install -y wget && \
    mkdir -p src/main/resources/static && \
    wget -O src/main/resources/static/MIREA_Gerb_Colour.png \
         https://www.mirea.ru/upload/medialibrary/80f/MIREA_Gerb_Colour.png && \
    apt-get clean && \
    rm -rf /var/lib/apt/lists/*

RUN gradle build --no-daemon -x test

FROM eclipse-temurin:21-jre

WORKDIR /app

ENV DB_HOST=postgres
ENV DB_PORT=5432
ENV DB_NAME=mirea_db
ENV DB_USERNAME=mirea_user
ENV DB_PASSWORD=mirea_password

COPY --from=build /app/build/libs/*.jar app.jar
COPY --from=build /app/src/main/resources/static/MIREA_Gerb_Colour.png /app/static/

EXPOSE 8080

ONBUILD RUN echo "Сборка и запуск произведены. Автор: Александр Грибков"

ENTRYPOINT ["java", "-jar", "app.jar"]
:::

::: {custom-style="Normal"}
Dockerfile использует многоэтапную сборку для оптимизации размера итогового образа. Первая стадия build использует образ gradle:8.14-jdk21 для компиляции приложения и загрузки герба МИРЭА. Вторая стадия использует минимальный образ eclipse-temurin:21-jre, содержащий только среду выполнения Java, и копирует из первой стадии только скомпилированный jar-файл и статические ресурсы.
:::

::: {custom-style="Normal"}
Переменные окружения для подключения к PostgreSQL определены в Dockerfile через директиву ENV. Порт базы данных получается из переменной окружения DB_PORT, что соответствует требованиям задания.
:::

::: {custom-style="Normal"}
В LABEL указаны ФИО и группа студента. Команда ONBUILD выводит сообщение с информацией об авторе при использовании данного образа как базового для других образов.

ОТВЕТЫ НА ВОПРОСЫ К ПРАКТИЧЕСКОЙ РАБОТЕ

::: {custom-style="Heading 2"}
Опишите процесс запуска приложения внутри контейнера Linux, используя Docker
:::

::: {custom-style="Normal"}
Процесс запуска приложения внутри контейнера Linux с использованием Docker начинается с создания Dockerfile, который содержит инструкции для сборки образа. Dockerfile определяет базовый образ с помощью директивы FROM, устанавливает зависимости через RUN, копирует файлы приложения с помощью COPY или ADD, и определяет команду запуска через ENTRYPOINT или CMD.
:::

::: {custom-style="Normal"}
После создания Dockerfile выполняется команда docker build для создания образа. Docker читает инструкции из Dockerfile и выполняет каждую из них последовательно, создавая слои образа. Каждая инструкция RUN, COPY и ADD создает новый слой, который представляет собой дельту изменений по сравнению с предыдущим слоем. Промежуточные слои кэшируются для ускорения последующих сборок.
:::

::: {custom-style="Normal"}
Когда образ создан, контейнер запускается с помощью команды docker run. Docker создает изолированное окружение на основе образа, включающее собственную файловую систему, сетевое пространство имен и пространство имен процессов. Контейнер получает копию файловой системы образа с дополнительным записываемым слоем поверх слоев образа, доступных только для чтения.
:::

::: {custom-style="Normal"}
При запуске контейнера Docker выполняет команду, определенную в ENTRYPOINT и CMD. Приложение запускается внутри изолированного окружения контейнера с заданными переменными окружения, сетевыми настройками и ограничениями ресурсов. Контейнер продолжает работать до тех пор, пока выполняется основной процесс, определенный в ENTRYPOINT или CMD.
:::

::: {custom-style="Heading 2"}
Что такое образ Docker и для чего он нужен?
:::

::: {custom-style="Normal"}
Docker-образ представляет собой шаблон для создания Docker-контейнеров. Это исполняемый пакет, содержащий все необходимое для запуска приложения: код, среду выполнения, библиотеки, переменные окружения и файлы конфигурации. Образ является неизменяемым и служит основой для создания множества идентичных контейнеров.
:::

::: {custom-style="Normal"}
Docker-образ состоит из слоев, где каждое изменение записывается в новый слой. Такая слоистая архитектура обеспечивает эффективное использование дискового пространства и ускорение передачи образов. При загрузке или скачивании Docker-образа операции производятся только с теми слоями, которые были изменены. Слои исходного Docker-образа являются общими между всеми его версиями и не дублируются.
:::

::: {custom-style="Normal"}
Образы Docker нужны для обеспечения портируемости приложений. Образ гарантирует, что приложение будет запускаться одинаково в любом окружении, имеющем Docker. Это решает проблему зависимостей и конфликтов версий библиотек, так как все зависимости упакованы внутри образа. Образы также упрощают развертывание приложений, позволяя быстро создавать новые экземпляры контейнеров на основе готового образа.
:::

::: {custom-style="Heading 2"}
Как соотносятся между собой файлы Dockerfile и Docker-Compose?
:::

::: {custom-style="Normal"}
Dockerfile и Docker Compose выполняют разные, но дополняющие друг друга функции в экосистеме Docker. Dockerfile представляет собой текстовый файл с инструкциями для создания одного Docker-образа. Он описывает, как собрать образ: какой базовый образ использовать, какие файлы копировать, какие команды выполнить и как запустить приложение.
:::

::: {custom-style="Normal"}
Docker Compose представляет собой инструмент для определения и запуска многоконтейнерных Docker-приложений. Файл docker-compose.yml описывает конфигурацию нескольких сервисов, их взаимодействие, сетевые настройки и тома для хранения данных. Docker Compose использует образы, которые могут быть созданы из Dockerfile или загружены из реестра.
:::

::: {custom-style="Normal"}
Связь между Dockerfile и Docker Compose заключается в том, что Docker Compose может ссылаться на Dockerfile для сборки образа определенного сервиса. В секции build файла docker-compose.yml указывается путь к директории с Dockerfile, и при выполнении docker-compose up образ собирается автоматически. Таким образом, Dockerfile описывает как создать один образ, а Docker Compose определяет как запустить и организовать взаимодействие нескольких контейнеров на основе этих образов.
:::

::: {custom-style="Heading 2"}
Что такое Dockerfile?
:::

::: {custom-style="Normal"}
Dockerfile представляет собой текстовый документ, который содержит все команды, необходимые для сборки Docker-образа. Это своего рода сценарий сборки, в котором последовательно перечислены инструкции для создания образа. Docker автоматически создает образы, читая инструкции из Dockerfile.
:::

::: {custom-style="Normal"}
Dockerfile придерживается определенного формата и набора инструкций. Каждая инструкция в Dockerfile создает слой в образе. Основные инструкции включают FROM для определения базового образа, RUN для выполнения команд во время сборки, COPY и ADD для копирования файлов, WORKDIR для установки рабочей директории, ENV для определения переменных окружения, EXPOSE для документирования портов, и CMD или ENTRYPOINT для указания команды запуска контейнера.
:::

::: {custom-style="Normal"}
Dockerfile обеспечивает воспроизводимость сборки образов. Один и тот же Dockerfile при сборке создаст идентичный образ независимо от окружения, в котором выполняется сборка. Dockerfile также служит документацией для образа, ясно показывая, какие зависимости установлены, какие файлы включены и как настроено приложение.
:::

::: {custom-style="Heading 2"}
Опишите политики перезапуска контейнера
:::

::: {custom-style="Normal"}
Docker предоставляет несколько политик перезапуска контейнеров, которые определяют поведение системы при остановке контейнера. Политика перезапуска задается с помощью флага --restart при запуске контейнера командой docker run.
:::

::: {custom-style="Normal"}
Политика no является значением по умолчанию и означает, что контейнер не будет автоматически перезапущен ни при каких обстоятельствах. Это подходит для контейнеров, которые выполняют разовые задачи или когда требуется полный контроль над жизненным циклом контейнера.
:::

::: {custom-style="Normal"}
Политика on-failure перезапускает контейнер только если процесс завершился с ненулевым кодом выхода, что указывает на ошибку. Можно дополнительно указать максимальное количество попыток перезапуска, например on-failure:5. Это полезно для приложений, которые могут временно сталкиваться с проблемами, но должны останавливаться при постоянных сбоях.
:::

::: {custom-style="Normal"}
Политика always указывает Docker всегда перезапускать контейнер, независимо от кода выхода. Если контейнер остановлен вручную, он будет перезапущен только после перезапуска демона Docker или ручного перезапуска контейнера. Эта политика подходит для сервисов, которые должны быть постоянно доступны.
:::

::: {custom-style="Normal"}
Политика unless-stopped аналогична always, но с одним отличием: если контейнер был остановлен вручную, он не будет автоматически перезапущен после перезагрузки демона Docker. Это позволяет администратору явно контролировать, какие контейнеры должны запускаться после перезагрузки системы.
:::

::: {custom-style="Heading 2"}
Назовите все возможные состояния контейнеров
:::

::: {custom-style="Normal"}
Контейнер Docker может находиться в одном из шести возможных состояний, каждое из которых отражает текущий этап его жизненного цикла.
:::

::: {custom-style="Normal"}
Состояние Created указывает, что контейнер создан, но еще не запущен. В этом состоянии все ресурсы для контейнера выделены, но процесс внутри контейнера не выполняется.
:::

::: {custom-style="Normal"}
Состояние Running означает, что контейнер активно работает и процесс внутри контейнера выполняется. Это основное рабочее состояние контейнера, в котором приложение обрабатывает запросы и выполняет свои функции.
:::

::: {custom-style="Normal"}
Состояние Restarting указывает, что контейнер находится в процессе перезапуска. Это временное состояние, которое возникает при применении политики автоматического перезапуска или при ручном перезапуске контейнера.
:::

::: {custom-style="Normal"}
Состояние Paused означает, что контейнер приостановлен. В этом состоянии все процессы контейнера заморожены, но их состояние сохранено в памяти. Контейнер может быть возобновлен командой docker unpause без потери состояния.
:::

::: {custom-style="Normal"}
Состояние Exited указывает, что контейнер закончил свою работу и остановлен. Процесс внутри контейнера завершился, но файловая система контейнера и его конфигурация сохранены. Контейнер может быть запущен снова командой docker start.
:::

::: {custom-style="Normal"}
Состояние Dead означает контейнер, который демон Docker попытался остановить, но не смог этого сделать. Это аварийное состояние, которое обычно указывает на проблемы с ресурсами или с самим Docker.
:::

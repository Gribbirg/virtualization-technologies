::: {custom-style="Heading 2"}
Создание Deployment для frontend
:::

::: {custom-style="Normal"}
Deployment представляет собой декларативный способ управления репликацией подов. Для клиентского приложения создан ресурс Deployment с двумя репликами.
:::

::: {custom-style="Listing"}
Манифест frontend.yaml
:::

::: {custom-style="Code"}
apiVersion: apps/v1
kind: Deployment
metadata:
  labels:
    app: frontend
  name: frontend
  namespace: default
spec:
  replicas: 2
  selector:
    matchLabels:
      app: frontend
  template:
    metadata:
      labels:
        app: frontend
    spec:
      containers:
      - image: gribkov/journal-server:v1
        imagePullPolicy: Never
        name: frontend
        env:
        - name: JOURNAL_ENTRIES
          valueFrom:
            configMapKeyRef:
              name: frontend-config
              key: journalEntries
        volumeMounts:
        - name: passwd-volume
          readOnly: true
          mountPath: "/etc/redis-passwd"
        resources:
          requests:
            cpu: "100m"
            memory: "256Mi"
          limits:
            cpu: "500m"
            memory: "512Mi"
      volumes:
        - name: passwd-volume
          secret:
            secretName: redis-passwd
:::

::: {custom-style="Normal"}
В манифесте установлены requests и limits для ресурсов CPU и памяти. Это обеспечивает гарантированное выделение ресурсов и ограничение их потребления.

Создание Service для frontend
:::

::: {custom-style="Normal"}
Service обеспечивает стабильную точку доступа к подам Deployment через балансировку нагрузки.
:::

::: {custom-style="Listing"}
Манифест traffic-service.yml для frontend
:::

::: {custom-style="Code"}
apiVersion: v1
kind: Service
metadata:
  labels:
    app: frontend
  name: frontend
  namespace: default
spec:
  ports:
  - port: 8080
    protocol: TCP
    targetPort: 8080
  selector:
    app: frontend
  type: ClusterIP
:::

::: {custom-style="Normal"}
Service типа ClusterIP делает приложение доступным только внутри кластера. Связь с подами осуществляется через метку app: frontend.

Создание ConfigMap
:::

::: {custom-style="Normal"}
ConfigMap используется для хранения конфигурационных данных в формате ключ-значение. В данном случае создается ConfigMap с параметром journalEntries.
:::

::: {custom-style="Listing"}
Команда создания ConfigMap
:::

::: {custom-style="Code"}
kubectl create configmap frontend-config --from-literal=journalEntries=10
:::

::: {custom-style="Normal"}
Эта конфигурация передается в контейнер как переменная среды JOURNAL_ENTRIES, что видно в манифесте Deployment.

::: {custom-style="Heading 2"}
Создание Secret для Redis
:::

::: {custom-style="Normal"}
Secret используется для хранения конфиденциальных данных, таких как пароли. Пароль для Redis генерируется случайным образом и сохраняется в Secret.
:::

::: {custom-style="Listing"}
Команда создания Secret с паролем Redis
:::

::: {custom-style="Code"}
kubectl create secret generic redis-passwd --from-literal=passwd=$(openssl rand -base64 32)
:::

::: {custom-style="Normal"}
Secret монтируется в контейнеры как том в каталог /etc/redis-passwd. Том создается в виде файловой системы tmpfs в оперативной памяти для повышения безопасности.

::: {custom-style="Heading 2"}
Развертывание Redis StatefulSet
:::

::: {custom-style="Normal"}
StatefulSet используется для развертывания stateful приложений с согласованными именами подов и постоянными томами. Redis развертывается с тремя репликами: одна master и две slave.
:::

::: {custom-style="Normal"}
Перед развертыванием Redis необходимо создать ConfigMap с скриптом launch.sh для настройки репликации.
:::

::: {custom-style="Listing"}
Скрипт launch.sh для настройки Master-Slave репликации
:::

::: {custom-style="Code"}
#!/bin/sh

PASSWORD=$(cat /etc/redis-passwd/passwd)
HOSTNAME=$(echo ${HOSTNAME})

if [ "${HOSTNAME}" = "redis-0" ]; then
    redis-server --requirepass "${PASSWORD}"
else
    redis-server --slaveof redis-0.redis 6379 --masterauth "${PASSWORD}" --requirepass "${PASSWORD}"
fi
:::

::: {custom-style="Normal"}
Скрипт проверяет имя хоста: если это redis-0, запускается master, иначе запускается slave с подключением к redis-0.
:::

::: {custom-style="Listing"}
Команда создания ConfigMap со скриптом
:::

::: {custom-style="Code"}
kubectl create configmap redis-config --from-file=launch.sh=app/redis/launch.sh
:::

::: {custom-style="Listing"}
Манифест redis.yml
:::

::: {custom-style="Code"}
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: redis
spec:
  serviceName: redis
  replicas: 3
  selector:
    matchLabels:
      app: redis
  template:
    metadata:
      labels:
        app: redis
    spec:
      containers:
      - name: redis
        image: redis:5-alpine
        ports:
        - containerPort: 6379
          name: redis
        volumeMounts:
        - name: data
          mountPath: /data
        - name: script
          mountPath: /script/launch.sh
          subPath: launch.sh
        - name: passwd-volume
          mountPath: /etc/redis-passwd
        command:
        - sh
        - -c
        - /script/launch.sh
      volumes:
      - name: script
        configMap:
          name: redis-config
          defaultMode: 0777
      - name: passwd-volume
        secret:
          secretName: redis-passwd
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: [ "ReadWriteOnce" ]
      resources:
        requests:
          storage: 10Gi
:::

::: {custom-style="Normal"}
StatefulSet создает три пода с именами redis-0, redis-1, redis-2. Для каждого пода автоматически создается PersistentVolumeClaim размером 10Gi.

::: {custom-style="Heading 2"}
Создание Services для Redis
:::

::: {custom-style="Normal"}
Для Redis создаются два Service: один для чтения данных и headless Service для записи.
:::

::: {custom-style="Listing"}
Service для чтения (redis-read.yml)
:::

::: {custom-style="Code"}
apiVersion: v1
kind: Service
metadata:
  labels:
    app: redis
  name: redis
  namespace: default
spec:
  ports:
  - port: 6379
    protocol: TCP
    targetPort: 6379
  selector:
    app: redis
  type: ClusterIP
:::

::: {custom-style="Normal"}
Этот Service балансирует запросы на чтение между всеми тремя репликами Redis.
:::

::: {custom-style="Listing"}
Headless Service для записи (redis-write.yml)
:::

::: {custom-style="Code"}
apiVersion: v1
kind: Service
metadata:
  labels:
    app: redis-write
  name: redis-write
spec:
  clusterIP: None
  ports:
  - port: 6379
  selector:
    app: redis
:::

::: {custom-style="Normal"}
Headless Service (clusterIP: None) создает отдельную DNS-запись для каждого пода. Для записи используется адрес redis-0.redis-write, который указывает на master.

:::

[Placeholder для скриншота]
:::

::: {custom-style="Picture name"}
Включение Ingress addon в Minikube
:::

::: {custom-style="Listing"}
Манифест ingress.yaml
:::

::: {custom-style="Code"}
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: frontend-ingress
spec:
  rules:
  - http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: frontend
            port:
              number: 8080
      - path: /
        pathType: Prefix
        backend:
          service:
            name: fileserver
            port:
              number: 80
:::

::: {custom-style="Normal"}
Ingress настроен на маршрутизацию запросов: путь /api направляется на frontend Service (порт 8080), а путь / на fileserver Service (порт 80). Важно, что правило для /api должно идти перед правилом для /, иначе все запросы будут перехватываться fileserver.

Ответы на вопросы
:::

::: {custom-style="Normal"}
1. Для чего нужен ресурс Deployment?
:::

::: {custom-style="Normal"}
Deployment используется для декларативного управления репликацией подов. Он обеспечивает автоматическое создание заданного количества идентичных реплик приложения, поддерживает механизмы поэтапного обновления (rolling updates), откат к предыдущим версиям, а также автоматическое восстановление подов в случае сбоев. Deployment сочетает возможности ReplicaSet с системой управления версиями.
:::

::: {custom-style="Normal"}
2. Почему не стоит хранить пароли в ConfigMap?
:::

::: {custom-style="Normal"}
ConfigMap предназначен для хранения обычных конфигурационных данных и не обеспечивает дополнительной защиты. Данные в ConfigMap хранятся в открытом виде и легко доступны через kubectl. Для конфиденциальных данных следует использовать Secret, который обеспечивает кодирование данных в base64 и может монтироваться как tmpfs том в памяти, не записываясь на диск.
:::

::: {custom-style="Normal"}
3. Что необходимо для настройки внешнего доступа для HTTP-трафика? Назовите шаги.
:::

::: {custom-style="Normal"}
Шаги настройки внешнего доступа:
:::

::: {custom-style="Normal"}
1. Создать Service типа ClusterIP для внутренней балансировки нагрузки между подами
2. Установить и настроить Ingress Controller в кластере (например, через minikube addons enable ingress)
3. Создать ресурс Ingress с правилами маршрутизации, указывающими соответствие между HTTP-путями и Service
4. Настроить DNS или использовать IP-адрес Ingress Controller для внешнего доступа
:::

::: {custom-style="Normal"}
4. Чем отличается развертывание stateful от развертывания клиентского приложения?
:::

::: {custom-style="Normal"}
Stateful приложения используют StatefulSet вместо Deployment. Основные отличия: StatefulSet обеспечивает согласованные имена подов (redis-0, redis-1, redis-2), определенный порядок создания и удаления подов, возможность использования PersistentVolumeClaim для каждого пода индивидуально. Клиентские приложения обычно stateless, используют Deployment с произвольными именами подов и не требуют постоянного хранилища.
:::

::: {custom-style="Normal"}
5. Где хранится том с секретными данными?
:::

::: {custom-style="Normal"}
Том с секретными данными создается в виде файловой системы tmpfs в оперативной памяти контейнера. Данные не записываются на диск, что повышает безопасность. Том монтируется в указанный каталог контейнера (например, /etc/redis-passwd) и доступен только для чтения.
:::

::: {custom-style="Normal"}
6. Как работает связка PersistentVolume и PersistentVolumeClaim?
:::

::: {custom-style="Normal"}
PersistentVolume (PV) представляет физический том хранилища в кластере. PersistentVolumeClaim (PVC) является запросом на выделение хранилища с определенными характеристиками (размер, режим доступа). Kubernetes автоматически связывает PVC с подходящим PV. В случае StatefulSet для каждого пода создается отдельный PVC через volumeClaimTemplates, что обеспечивает изолированное хранилище для каждой реплики stateful приложения.
:::

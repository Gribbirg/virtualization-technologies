Создание Pod с ограничениями памяти
:::

::: {custom-style="Normal"}
Создается Pod с корректными ограничениями памяти. Для контейнера устанавливается запрос памяти (request) в 100 MiB и лимит (limit) в 200 MiB. Контейнер попытается использовать 150 MiB памяти, что находится в пределах установленного лимита.
:::

::: {custom-style="Listing"}
Конфигурационный файл memory-request-limit.yaml
:::

::: {custom-style="Code"}
apiVersion: v1
kind: Pod
metadata:
  name: memory-demo
  namespace: gribkov-as-ikbo-16-22
spec:
  containers:
  - name: memory-demo-ctr
    image: polinux/stress
    resources:
      limits:
        memory: "200Mi"
      requests:
        memory: "100Mi"
    command: ["stress"]
    args: ["--vm", "1", "--vm-bytes", "150M", "--vm-hang", "1"]
:::

::: {custom-style="Normal"}
Раздел args содержит аргументы для контейнера. Аргументы --vm-bytes 150M указывают контейнеру попытаться занять 150 MiB памяти.

Вывод
:::

::: {custom-style="Normal"}
В результате выполнения практической работы были изучены механизмы управления ресурсами в Kubernetes. Достигнуты следующие результаты:
:::

::: {custom-style="Normal"}
1. Запущен сервер метрик в minikube для сбора информации об использовании ресурсов
2. Создано отдельное пространство имён для изоляции ресурсов практической работы
3. Изучены механизмы работы requests и limits для памяти:
   - Pod с корректными ограничениями успешно работает в пределах выделенных ресурсов
   - При превышении лимита памяти контейнер убивается kubelet с ошибкой OOMKilled
   - Pod с недостижимым запросом памяти остается в статусе Pending
4. Изучены механизмы работы requests и limits для CPU:
   - CPU ограничивается через throttling, контейнер не завершается при попытке превысить лимит
   - Pod с недостижимым запросом CPU не может быть запланирован на ноде
5. Понято назначение QoS-классов в Kubernetes:
   - Guaranteed: requests равны limits для всех ресурсов
   - Burstable: requests меньше limits хотя бы для одного ресурса
   - Best Effort: не установлены ограничения
:::

::: {custom-style="Normal"}
Работа продемонстрировала важность корректной настройки ограничений ресурсов для обеспечения стабильности кластера и справедливого распределения ресурсов между приложениями.

Ответы на вопросы
:::

::: {custom-style="Normal"}
1. Назовите 3 QoS-класса
:::

::: {custom-style="Normal"}
Три QoS-класса в Kubernetes:
:::

::: {custom-style="Normal"}
- Guaranteed: назначается когда для каждого контейнера в поде для memory и cpu задан request и limit, причем эти значения совпадают. Такие поды имеют наивысший приоритет и вытесняются последними.
:::

::: {custom-style="Normal"}
- Burstable: назначается когда хотя бы один контейнер в поде имеет request или limit, при этом request меньше limit. Эти поды имеют средний приоритет вытеснения.
:::

::: {custom-style="Normal"}
- Best Effort: назначается когда ни один контейнер в поде не ограничен по ресурсам. Такие поды первыми кандидаты на вытеснение при нехватке ресурсов на ноде.
:::

::: {custom-style="Normal"}
2. Назовите основные ресурсы системы и единицы их измерения в Kubernetes
:::

::: {custom-style="Normal"}
Основные типы ресурсов в Kubernetes:
:::

::: {custom-style="Normal"}
- CPU: измеряется в ядрах. Можно указывать дробные значения (0.5) или в милли-CPU (500m = 0.5 CPU). 1 CPU соответствует одному виртуальному ядру на облачном провайдере или одному гипертреду на физическом процессоре.
:::

::: {custom-style="Normal"}
- Memory (RAM): измеряется в байтах. Используются суффиксы: Ki (кибибайт), Mi (мебибайт), Gi (гибибайт). Также допустимы суффиксы степеней десяти: K, M, G.
:::

:::

::: {custom-style="Normal"}
HPA (Horizontal Pod Autoscaler) используется для автоматического масштабирования количества подов в зависимости от использования ресурсов. HPA работает по следующему алгоритму:
:::

::: {custom-style="Normal"}
- Определяет текущие показания наблюдаемого ресурса (currentMetricValue)
- Определяет желаемые значения для ресурса (desiredMetricValue), которые задаются через request
- Рассчитывает желаемое количество реплик по формуле: desiredReplicas = currentReplicas * (currentMetricValue / desiredMetricValue)
- Масштабирование не происходит, если коэффициент близок к 1 (с учетом допустимой погрешности)
:::

::: {custom-style="Normal"}
4. Для чего необходимо устанавливать ограничения в Kubernetes?
:::

::: {custom-style="Normal"}
Установка ограничений в Kubernetes необходима по следующим причинам:
:::

::: {custom-style="Normal"}
- Предотвращение потребления одним подом всех ресурсов ноды, что может привести к отказу других приложений
- Корректное планирование подов на нодах: scheduler использует requests для определения достаточности ресурсов на ноде
- Обеспечение справедливого распределения ресурсов между приложениями
- Защита от утечек памяти и runaway процессов
- Определение QoS-класса пода, который влияет на приоритет вытеснения при нехватке ресурсов
:::

::: {custom-style="Normal"}
5. Что будет с узлом при превышении ограничений?
:::

::: {custom-style="Normal"}
При превышении ограничений происходит следующее:
:::

::: {custom-style="Normal"}
- При превышении memory limit: контейнер немедленно убивается kubelet с ошибкой OOMKilled (Out Of Memory). После этого контейнер может быть перезапущен в соответствии с политикой перезапуска пода.
:::

::: {custom-style="Normal"}
- При превышении CPU limit: процесс ограничивается через механизм throttling (троттлинг). Контейнер не завершается, но его процессорное время ограничивается установленным лимитом.
:::

::: {custom-style="Normal"}
- При нехватке ресурсов на ноде: kubelet начинает ранжировать и вытеснять поды по определенному алгоритму, учитывающему приоритет пода и его QoS-класс. При одинаковом приоритете в первую очередь вытесняются поды с классом Best Effort, затем Burstable, и в последнюю очередь Guaranteed.
:::
